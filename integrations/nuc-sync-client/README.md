# ตัวดึงข้อมูล salechatbot → MongoDB ของ NUC-Kay

ดึงข้อมูลจาก PostgreSQL ของแชทบอทผ่าน **HTTPS สาธารณะอย่างเดียว** ไม่ต้องต่อ LAN ไม่ต้องเปิดพอร์ตฝั่ง NUC
(NUC เป็นฝ่ายเรียกออกทุกครั้ง — เซิร์ฟเวอร์แชทบอทไม่เคยเรียกเข้ามาหา NUC เลย)

> รายละเอียดของตัว API เอง (endpoint, พารามิเตอร์, กฎการดึงที่ถูกต้อง, รหัสข้อผิดพลาด)
> อยู่ที่ [`docs/SYNC_API.md`](../../docs/SYNC_API.md) — ไฟล์นี้พูดถึงเฉพาะตัวดึงฝั่ง NUC

ยืนยันแล้วว่าเส้นทาง LAN ใช้ไม่ได้จริง: เซิร์ฟเวอร์แชทบอทอยู่ `192.168.100.17/24` ส่วน NUC อยู่
`192.168.109.69` คนละ subnet และ TCP ยิงไม่ถึงกัน

## ติดตั้งบน NUC

ต้องมี **Node 20.6 ขึ้นไป** — ใช้ `fetch` ที่มากับ Node และ `--env-file` ที่เพิ่งมีใน 20.6
(ถ้าติดอยู่ที่ Node 18 ให้ `set -a; . ./.env; set +a` แล้วเรียก `node pull.mjs` เปล่า ๆ แทน)

```bash
cd /opt/nuc-sync-client          # หรือที่ไหนก็ได้
npm install                      # ลงแพ็กเกจเดียว: mongodb
cp .env.example .env             # แล้วเติม SYNC_API_KEY ที่ได้จากฝั่งแชทบอท
```

ขอกุญแจจากฝั่งแชทบอท (สั่งบนเซิร์ฟเวอร์แชทบอท):

```bash
docker compose exec app npm run sync:key -- --name "NUC-Kay"
```

กุญแจแสดงครั้งเดียว ทำหายต้องออกใหม่ · เพิกถอนด้วย `npm run sync:key -- --revoke <id>`

## รัน

```bash
node --env-file=.env pull.mjs              # ดึงทุกตารางที่ถึงรอบ (ใช้กับ cron)
node --env-file=.env pull.mjs --table products   # ตารางเดียว ข้ามการเช็ครอบ
node --env-file=.env pull.mjs --full             # ล้าง cursor ดึงใหม่ทั้งหมด
node --env-file=.env pull.mjs --reconcile        # บังคับไล่ลบแถวที่ต้นทางลบไปแล้ว
```

ตั้งให้วิ่งเองทุก 10 นาที (cron ของ user ธรรมดา ไม่ต้อง root):

```cron
*/10 * * * * cd /opt/nuc-sync-client && /usr/bin/node --env-file=.env pull.mjs >> /var/log/nuc-sync.log 2>&1
```

สคริปต์เป็นแบบ "รันจบแล้วออก" ไม่ใช่ daemon โดยเจตนา — process ที่ตายเงียบคือโหมดพังที่เจอบ่อยที่สุด
ของตัว sync แบบอยู่ยาว ส่วน cron ที่ไม่วิ่งจะเห็นได้จาก log ที่หยุดเดิน

## ข้อมูลมาลงยังไง

- collection ชื่อเดียวกับตารางฝั่ง Postgres
- `_id` = primary key ฝั่ง Postgres เสมอ (คีย์ประกอบต่อกันด้วย `|` เช่น `customers` = `company_id|contact_id`)
  → ดึงซ้ำกี่รอบก็ทับแถวเดิม ไม่มีทางเกิดซ้ำ
- `_syncedAt` = เวลาที่แถวนี้ถูกเขียนล่าสุด
- สถานะการดึงเก็บใน collection `_sync_state` (ตารางละ 1 เอกสาร: cursor, เวลาที่สำเร็จล่าสุด, ข้อผิดพลาดล่าสุด)

**ระวังเรื่องชนิดข้อมูล:** คอลัมน์ `numeric` ของ Postgres (ยอดเงิน, จำนวน) มาเป็น **สตริง** ไม่ใช่ตัวเลข
— ตั้งใจให้เป็นแบบนั้นเพราะการแปลงเป็น double ของ JS ทำให้ทศนิยมเพี้ยน ถ้าฝั่ง NUC ต้องคำนวณเงิน
ให้แปลงเป็น `Decimal128` ตอนเขียนลง Mongo อย่าใช้ `parseFloat` ตรง ๆ
ส่วน timestamp มาเป็นสตริง ISO 8601

## 3 โหมดของการ sync (ฝั่งเซิร์ฟเวอร์เป็นคนบอกมาใน manifest)

| โหมด | ใช้กับ | ทำงานยังไง |
|---|---|---|
| `incremental` | `sale_orders`, `customers`, `products`, `quotations` | ดึงเฉพาะที่เปลี่ยนหลังรอบก่อน แล้ว upsert ทับ |
| `append` | `messages`, `api_logs` | เดินต่อจาก id ล่าสุดที่ดึงมา |
| `snapshot` | ตารางตั้งค่า/กฎ/ทะเบียนที่มีการลบแถว | ดึงยกตาราง แล้วลบสิ่งที่ไม่ได้มากับรอบนี้ทิ้ง |

**ตารางที่ต้นทางลบแถวได้จริงมีตัวเดียวคือ `quotations`** (ล้างใบค้าง/ยกเลิกใบ) จึงต้องไล่เทียบรายการ id
เป็นรอบ ๆ เพื่อลบตาม — ค่าตั้งต้นคือทุก 60 นาที (`RECONCILE_EVERY_MINUTES`)
ส่วน `sale_orders` / `customers` / `products` ต้นทางเป็น upsert ล้วน ไม่มีการลบ จึงไม่ต้องไล่เทียบ

`customers_data_view` เป็นตารางสรุปที่ต้นทางสร้างใหม่ทั้งใบเป็นรอบ ๆ (82,000 แถว / 41 MB) จึงตั้งให้ดึง
วันละครั้ง และถ้าต้นทางสร้างใหม่ระหว่างที่กำลังไล่หน้าอยู่ สคริปต์จะทิ้งของที่ได้มาครึ่ง ๆ แล้วเริ่มใหม่เอง
(ดูจากค่า `generation` ที่แนบมาทุกหน้า) — ถ้าไม่อยากดึงก้อนนี้เลย ใส่ชื่อตารางที่ต้องการใน `TABLES` แทน

## รอบแรกใช้เวลานาน

ครั้งแรกต้องดึงทั้งฐาน ~610 MB (`sale_orders` 429 MB เป็นก้อนใหญ่สุด) วัดจริงได้ ~3.7 MB ต่อหน้า
ที่ `PAGE_LIMIT=2000` หน้าละ ~0.16 วินาที → ทั้ง `sale_orders` ประมาณ 25-30 วินาทีของเวลาเซิร์ฟเวอร์
บวกเวลาเขียน Mongo **ให้รันรอบแรกนอกเวลาทำงาน** รอบถัด ๆ ไปจะเหลือแค่หลักร้อย KB

## เวลาพัง

- **401** — กุญแจผิด/ถูกเพิกถอน · ขอใหม่จากฝั่งแชทบอท
- **429** — มีตัวดึงยิงพร้อมกันเกิน 4 เส้น (เพดานฝั่งเซิร์ฟเวอร์ ตั้งไว้กัน DB ของแชทบอทโดนถล่ม)
  สคริปต์รอตาม `Retry-After` แล้วลองใหม่เอง · ถ้าเจอบ่อยแปลว่า cron ยิงทับกัน = รอบก่อนยังไม่จบ
- **ตารางเดียวพัง ตารางอื่นยังไปต่อ** — cursor ของตารางที่พังจะไม่ถูกบันทึก รอบหน้าจึงเริ่มจากจุดเดิมเอง
  ดูสาเหตุล่าสุดได้ที่ `_sync_state` ฟิลด์ `last_error` / `last_error_at`
